# 小满记账智能周报与月报设计

日期：2026-09-17

## 1. 结论

小满不应继续用“本期总支出 + 最大分类 + 固定建议”的报告模板。报告应由四层组成：

```text
账单与预算数据
  -> 确定性事实计算
  -> 候选洞察检测
  -> 价值与置信度排序
  -> 规则文案或受约束的 AI 润色
```

每期报告只展示最值得用户关注的 3 至 5 条内容。没有显著变化时，应展示“本期消费节奏稳定”和相应证据，不为填满页面制造建议。

推荐采用“规则与统计负责结论，语言模型只负责表达”的混合方案。它比纯模板更个性化，比直接把全部流水交给大模型更准确、更便宜，也更容易解释和测试。

## 2. GitHub 项目研究结论

### 2.1 Actual Budget

项目：[actualbudget/actual](https://github.com/actualbudget/actual)

可借鉴能力：

- 支持 3、6、12 个月、年初至今和全部历史等不同平均基线。
- 使用线性回归计算趋势线，而不是只比较相邻两个周期。
- 把预算额、实际支出、结余、超支结转分别计算。
- 现金流预测会把账户余额、计划交易和重复交易放进同一条时间线。
- 报告数据计算与图表显示分离，用户可以过滤日期、账户和分类。

对小满的启发：周报不能只与上周比较，月报不能只与上月比较。应同时提供“相邻周期”和“个人历史基线”，避免旅行、开学、节假日等偶发周期造成误判。

### 2.2 Firefly III

项目：[firefly-iii/firefly-iii](https://github.com/firefly-iii/firefly-iii)

可借鉴能力：

- 先统一金额方向和币种，再进行汇总。
- 将账户、分类、预算、无预算支出和转账分别聚合。
- 月报页面本身只负责组装，真正的数据结论来自独立聚合器。
- 同时展示平均支出、最大支出、按分类和按账户的交叉统计。

对小满的启发：报告生成器不应直接查询杂乱流水并拼文案。需要先形成稳定的“周期事实快照”，页面和通知只消费快照。

### 2.3 Helius Finance Tracker

项目：[Helius-Finance/helius-finance-tracker](https://github.com/Helius-Finance/helius-finance-tracker)

可借鉴能力：

- 把固定账单、重复交易、预算和账户余额组合成逐日现金流预测。
- 检测预计余额首次为负的日期。
- 对存钱目标计算剩余金额、建议月存金额和是否按计划完成。
- 预算状态明确区分预算、已花、剩余和是否超支。

对小满的启发：月报不只总结过去，还应回答“照这个速度继续，下个月会怎样”。首版可做简单的月末支出预测，不需要一开始引入复杂机器学习。

### 2.4 Ghostfolio

项目：[ghostfolio/ghostfolio](https://github.com/ghostfolio/ghostfolio)

可借鉴能力：

- 每个洞察是独立规则，拥有自己的阈值、启用状态和计算结果。
- 规则只返回明确的通过、不通过及证据文案。
- 用户可以调整部分阈值。
- 昂贵的基准计算使用缓存，并在后台更新。

对小满的启发：把“餐饮上升”“预算过快”“高频小额”“储蓄不足”等做成独立检测器，不要塞进一个越来越长的函数。

### 2.5 许可证边界

- Actual Budget 适合参考其数据流、基线和趋势设计。
- Firefly III 与 Helius 使用 AGPL 系列许可证，不直接复制源码；小满只采用公开的统计思想并独立实现。
- 所有引入的第三方代码在落地前必须再次核对许可证和声明要求。

## 3. 小满当前实现审计

当前 `ReportInsightEngine` 已具备最小骨架：

- 计算本期总支出、账单数、活跃天数。
- 计算最大支出分类及占比。
- 比较上一个周期的总支出。
- 数据达到 5 笔且覆盖 3 天后，可能给出一条“最大分类减少 10%”的建议。

当前主要问题：

1. 基线只有上周或上月，容易被偶发消费误导。
2. 只分析支出总额和最大分类，没有解释“变化由谁造成”。
3. 固定减少最大分类的 10%，不一定可执行，也没有区分房租和奶茶。
4. 没有预算消耗速度、异常交易、固定支出、高频小额、无消费日和储蓄率。
5. 周报与月报调用同一套逻辑，只改 `period` 字符串，没有体现周期差异。
6. 数据模型只有金额、分类、日期和备注；缺少商家、支付账户、来源、更新时间和退款关联，限制了洞察质量。
7. 当前使用浮点数计算金额，长期应迁移为整数分或 Decimal，避免金额误差。

## 4. 三种实现路线

### 方案 A：继续扩展固定模板

优点：开发最快、无模型费用。

缺点：规则互相缠绕，用户很快发现每期说法雷同，不能算真正智能。

结论：不采用。

### 方案 B：全部流水交给语言模型

优点：表面上灵活，原型快。

缺点：可能算错金额、遗漏账单或编造原因；成本和隐私压力高；难以复现和测试。

结论：不采用。

### 方案 C：确定性洞察引擎 + 可选 AI 表达

优点：金额可靠、结果可解释、可测试；无显著洞察时可以零模型成本；以后可以平滑升级表达质量。

缺点：需要先建设事实层和规则体系。

结论：采用。

## 5. 数据架构

### 5.1 周期事实快照

新增 `ReportSnapshot`，按用户、报告类型和周期存储聚合结果，不保存模型自行计算的金额。

```json
{
  "report_type": "weekly",
  "period": "2026-W38",
  "generated_at": "2026-09-20T09:00:00+08:00",
  "data_version": "record-count:max-created-at:max-updated-at",
  "coverage": {
    "transaction_count": 24,
    "active_days": 6,
    "categorized_ratio": 0.96,
    "confidence": 0.92
  },
  "metrics": {},
  "insights": []
}
```

### 5.2 账单数据补强

为了让报告真正智能，建议逐步为账单增加：

- `amount_minor`：整数分，逐步替代浮点金额。
- `merchant_name` 与 `merchant_key`：支持商家集中度和重复消费。
- `account_id`：支持账户现金流和余额预测。
- `source`：manual、ocr、voice、import。
- `updated_at`：保证编辑账单后报告缓存失效。
- `refund_of_record_id`：避免退款被当作普通收入。
- `is_recurring` 或重复交易识别结果。

第一阶段即使不迁移数据库，也能基于现有金额、分类、日期和备注完成核心洞察。

## 6. 事实指标

### 6.1 周报指标

- 本周收入、支出、存钱、净结余、储蓄率。
- 与上周、近 4 个完整周均值、近 8 周中位数比较。
- 各大类和子类支出、占比及对总变化的贡献。
- 每日支出、活跃记账天数、无消费日。
- 高频小额支出：同分类或商家、金额较小、出现次数多。
- 单笔大额和统计异常支出。
- 钱包预算本周应有进度与实际进度。
- 连续趋势：至少 3 个周期同方向变化。

### 6.2 月报指标

- 本月收入、支出、存钱、结余、储蓄率。
- 与上月、近 3 月均值、近 6 月中位数比较。
- 固定支出、可变支出、必要支出和弹性支出。
- 预算完成率、超支金额、预算覆盖率和无预算支出。
- 分类结构变化和新增高支出分类。
- 商家集中度、订阅或重复扣款候选。
- 月末支出预测和预计预算结余。
- 存钱目标进度与建议月存金额。

## 7. 候选洞察检测器

每个检测器只负责一个问题，返回统一结构：

```json
{
  "id": "category_food_rise_2026W38",
  "kind": "category_change",
  "severity": 0.74,
  "confidence": 0.91,
  "novelty": 0.65,
  "actionability": 0.85,
  "evidence_ids": ["food-current", "food-baseline"],
  "values": {
    "category": "餐饮",
    "current": 482.0,
    "baseline": 326.0,
    "change_amount": 156.0,
    "change_pct": 47.9,
    "contribution_pct": 63.0
  }
}
```

首批检测器：

1. `PeriodChangeDetector`：总支出明显上升或下降。
2. `CategoryContributionDetector`：找出总变化的主要推动分类。
3. `BudgetPaceDetector`：根据周期已过比例判断花费速度。
4. `OutlierTransactionDetector`：检测异常大额，不使用容易被极端值影响的均值。
5. `SmallFrequentSpendDetector`：识别高频小额累计。
6. `TrendDetector`：检测连续 3 至 6 个周期趋势。
7. `SavingsRateDetector`：储蓄率变化与目标差距。
8. `StablePeriodDetector`：在没有显著变化时生成诚实的稳定结论。

第二阶段再增加重复扣款、商家集中度、现金流风险和目标预测。

## 8. 算法规则

### 8.1 基线

周报同时计算：

- 上一个完整周。
- 近 4 个完整周平均值。
- 近 8 个完整周中位数。

月报同时计算：

- 上一个完整月。
- 近 3 个完整月平均值。
- 近 6 个完整月中位数。

默认结论优先使用中位数或截尾均值，减少偶发大额造成的误导；页面可以补充显示相邻周期变化。

### 8.2 异常检测

账单金额使用 MAD，而不是只使用标准差：

```text
median = 金额中位数
MAD = median(|x - median|)
robust_z = 0.6745 * (x - median) / MAD
```

当 `robust_z >= 3.5` 且金额超过用户该分类历史中位数的合理下限时，才标记异常。样本少于 8 笔时不下强结论，只标记为“大额账单”。

### 8.3 分类贡献

```text
分类变化额 = 本期分类支出 - 基线分类支出
贡献度 = 正向分类变化额 / 所有正向分类变化额之和
```

只有同时满足以下条件才进入候选：

- 变化额超过用户本期总支出的 5%，或超过一个绝对金额下限。
- 变化比例超过 20%。
- 贡献度超过 25%。

绝对金额下限应根据用户月均支出动态计算，不固定写死为 100 元。

### 8.4 预算速度

```text
时间进度 = 已过天数 / 周期总天数
预算进度 = 已支出 / 预算
速度比 = 预算进度 / 时间进度
```

- 速度比小于 0.9：节奏安全。
- 0.9 至 1.1：接近计划。
- 大于 1.1：需要留意。
- 大于 1.3 且剩余预算不足：高优先级提醒。

必须处理发薪日周期，不强制所有用户按自然月计算。

### 8.5 高频小额

候选条件：

- 单笔金额低于该用户支出中位数或用户定义的小额阈值。
- 同一分类或商家在一周出现至少 3 次、一个月至少 6 次。
- 累计金额占本期支出的比例达到 5%。

建议不能简单要求“全部戒掉”，而应给出减少次数后的可计算结果。例如从每周 5 次调整到 3 次，潜在节省金额由历史单笔中位数计算。

## 9. 洞察排序与去重

每条候选计算价值分：

```text
score =
  severity * 0.30
  + confidence * 0.25
  + actionability * 0.25
  + novelty * 0.20
```

规则：

- 同一分类最多展示一条主洞察，避免三条建议都在说餐饮。
- 至少保留一条正向或稳定反馈，避免报告只制造焦虑。
- 周报最多 3 条核心洞察，月报最多 5 条。
- 置信度低于 0.55 不展示；0.55 至 0.75 使用“可能、看起来”等弱表达；高于 0.75 才使用确定表达。
- 洞察与上期相同且变化不明显时降低 `novelty`，避免重复唠叨。

## 10. 文案生成

### 10.1 默认规则文案

不调用模型也能生成完整报告：

```text
发现：本周餐饮支出 ¥482，比近 4 周均值高 ¥156。
影响：餐饮贡献了本周支出增长的 63%。
下一步：如果下周少点 2 次外卖，按你的历史单次中位数估算，可少支出约 ¥46。
```

所有数字必须来自 `evidence_ids` 对应事实。

### 10.2 可选 AI 润色

语言模型只接收聚合后的 3 至 5 条候选洞察，不接收全部原始流水。模型输出必须是结构化 JSON，并满足：

- 每句话引用已有 `insight_id` 或 `evidence_id`。
- 不允许新增输入中不存在的金额、比例、日期和分类。
- 最多改写表达，不改变建议动作和估算值。
- 校验失败时立即回退到规则文案。

无显著洞察、用户未开启 AI 表达或缓存有效时，不调用模型。

## 11. 周报与月报的产品差异

### 周报

目标是帮助用户在行为还来得及调整时发现变化。

页面重点：

- 一句话本周结论。
- 与个人近 4 周节奏比较。
- 1 至 3 个可在下周执行的小动作。
- 点击洞察可查看对应账单证据。

### 月报

目标是复盘结构、预算和未来风险。

页面重点：

- 收支、结余、储蓄率和预算总览。
- 与近 3 至 6 月基线比较。
- 固定与可变支出结构。
- 下月预测、存钱目标和预算调整建议。
- 用户可以接受、忽略或调整某条建议，作为后续个性化信号。

## 12. API 建议

```text
GET /api/v1/reports/weekly?period=2026-W38
GET /api/v1/reports/monthly?period=2026-09
POST /api/v1/reports/{report_id}/feedback
POST /api/v1/reports/{report_id}/refresh
```

报告响应统一为：

```json
{
  "summary": {},
  "coverage": {},
  "facts": [],
  "insights": [],
  "forecast": null,
  "generated_at": "...",
  "data_version": "..."
}
```

旧 `/stats/weekly`、`/stats/monthly` 可以暂时保留兼容，但前端报告页面最终只使用统一报告接口。

## 13. 缓存与成本

缓存键：

```text
user_id + report_type + period + record_count + max_created_at + max_updated_at + rules_version
```

策略：

- 打开报告时优先返回有效快照。
- 新增、编辑或删除本周期账单后使缓存失效。
- 通知只提示报告已生成，不在通知调度线程重新计算全部洞察。
- AI 文案独立缓存，规则或数据没有变化时不重复调用。
- 先执行规则筛选，只有进入最终展示的洞察才可能调用小模型。

## 14. 分阶段实施

### 第一阶段：可信事实层

- 拆分当前 `ReportInsightEngine`。
- 增加多周期基线、分类贡献、预算速度、MAD 异常和稳定周期检测。
- 周报与月报使用不同指标配置。
- 补充数据充分度与置信度。
- 全部使用规则文案，暂不接模型。

### 第二阶段：个性化与反馈

- 增加高频小额、连续趋势、固定支出和商家集中度。
- 支持“有帮助、忽略、不再提醒此类”反馈。
- 使用历史反馈调整规则启用状态和排序，不修改事实计算。

### 第三阶段：预测与 AI 表达

- 接入重复账单、账户余额和钱包预算，生成月末预测。
- 增加存钱目标建议月存金额。
- 可选接入小模型润色，严格校验数字和证据引用。

## 15. 测试与验收

后端单元测试至少覆盖：

- 少量数据不生成强建议。
- 周跨年、月跨年和不完整当前周期。
- 上一周期异常但长期基线稳定时不误报。
- 分类变化贡献度之和与总变化一致。
- MAD 为零、样本不足和退款场景。
- 大类和子类合并时不重复计数。
- 发薪日周期的预算速度。
- 金额只来自事实层，文案层不能引入新数字。
- 缓存随新增、编辑和删除账单失效。

产品验收：

- 连续 8 周相同消费数据不会每周重复同一句无价值建议。
- 修改一笔账单分类后，相关洞察和证据同步变化。
- 用户可以从每条洞察进入对应账单列表。
- 无网络或模型不可用时，报告仍完整可读。
- 一般用户生成规则报告不产生模型费用。

## 16. 首版应交付的最小闭环

首版不要一次实现所有预测和 AI。最小可用闭环为：

1. 多周期基线。
2. 分类变化贡献。
3. 预算速度。
4. 异常大额。
5. 高频小额。
6. 稳定周期结论。
7. 洞察排序与去重。
8. 每条洞察可查看证据账单。

完成这八项后，小满的周报和月报就已经从“模板统计页”升级为“基于个人行为的解释型报告”。预测和 AI 润色应在这套事实基础稳定后再加入。
